**`listFiles()` が null を返す分岐は本ラウンドでテスト済み**（`SendSyncSupportTest#testGetTimestampSignatureWhenFilesCanNotBeListed`、`:301`）。一時ディレクトリに `setReadable(false)` を行い `org.junit.Assume.assumeTrue` で `listFiles() == null` になる環境かをガードしてから検証する。実測環境では `Skipped: 0` で実際に到達し、`getTimestampSignature` は LINE 11/11・BRANCH 6/6。ただし **root 実行の Docker CI・Windows・WSL の DrvFs ではこの `Assume` が無言で発火し、当該分岐が未検証・未カバーになる**（Verification が M6 で killer を1件と確定）。この環境依存は残す。

**`Arrays.sort(files)` の走査順非依存は、テストで担保できない。** `listFiles()` は未変更ディレクトリに対し同一プロセス内で決定的に同じ順序を返すため、ソートを削除しても全848テストが通ることを3エキスパートが別々に実測した。列挙順を注入できる seam を設けない限り検証手段がない。指摘 H の決定次第で、この未カバー項目自体を消せる（選択肢 B・C）。

**署名の衝突は、確率的ではなく構造的なクラスとして存在する。** `signature * 31 + child` はエントリ名も構造区切りも畳み込まないため、ディレクトリ直下のファイルとサブディレクトリの係数がどちらも 31 になり、両者の `lastModified` が入れ替わると署名が一致する（Craft が実測再現）。ただし**単一ファイルの変更は必ず検知される**（係数 `31^k` は奇数で mod 2^64 可逆）。衝突には2つ以上の `lastModified` が逆方向へ厳密に 31:1 の比で動く必要があり、編集・再生成・チェックアウトのいずれでも起きない。指摘 H の決定次第で解消する（選択肢 A・B は衝突クラスを縮小、C は衝突そのものを消す）。
