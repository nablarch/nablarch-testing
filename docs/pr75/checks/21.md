## 未カバーのまま残す判断

本ラウンドで `SendSyncSupport.java` の `listFiles()` が null を返す分岐（`:433-436`）のテストを追加した（`SendSyncSupportTest#testGetTimestampSignatureWhenFilesCanNotBeListed`、`:301`）。一時ディレクトリに `setReadable(false)` を行い、`org.junit.Assume.assumeTrue` で `listFiles() == null` になる環境かをガードしてから検証する（root 実行等で条件を作れない場合はクリーンにスキップする）。検証後は `finally` で `setReadable(true)` に戻す。実測環境では `Skipped: 0` で実際に到達しており、`getTimestampSignature` は LINE 11/11・BRANCH 6/6 で未カバー箇所なし。

未カバーのまま残すのは、`getTimestampSignature` が返す**署名の衝突**である。ディレクトリ配下の最終更新日時を `signature * 31 + child` で畳み込んだ値であるため、内容が異なるにも関わらず署名が一致し再読み込みが行われない可能性が確率的に残る。これはテストで網羅できる性質のものではないため、`getTimestampSignature` の Javadoc に明記して残す。
